# Data Model Suggestion 3: Event-Sourced / Audit-First

> Project: Retail Store Analytics · Created: 2026-05-29

## Philosophy

This model treats every foot traffic count, POS transaction, sensor reading, staff shift, schedule change, weather update, and basket analysis run as an immutable event. The store's operational state — conversion rate, staffing level, visitor trend — is not a mutable record but a projection computed by replaying traffic and transaction events. Staff scheduling recommendations are events generated by the forecasting engine. Basket association rules are events produced by periodic mining jobs.

Retail analytics benefits from event sourcing because the core analytical value is temporal: "why was conversion lower on Saturday?" requires correlating traffic events, transaction events, staffing events, and weather events at the same time window. An event-sourced model preserves the exact temporal sequence, enabling retroactive analysis when data arrives late (POS batch uploads), causal investigation of operational anomalies, and permanent recording of every AI-generated scheduling recommendation.

**Best for:** Multi-store retail operations requiring full temporal operational audit trails, causal analysis of conversion anomalies (correlating traffic, staffing, weather, and promotions), and permanent recording of AI-generated scheduling recommendations.

**Trade-offs:**
- (+) Full temporal correlation: traffic + transactions + staffing + weather at any time window
- (+) Late-arriving POS data replayed into projections without backfilling
- (+) Every AI scheduling recommendation permanently recorded for operational review
- (+) New metrics added by creating new projections — no schema migration
- (-) Read models must be maintained for dashboard views
- (-) Current store performance requires read model, not direct query
- (-) High event volume from sensors (potentially per-second) requires careful granularity choices
- (-) More complex for non-technical store managers to understand

## Event Infrastructure

```sql
CREATE TABLE event_store (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    stream_type     TEXT NOT NULL CHECK (stream_type IN (
        'tenant', 'user', 'store', 'sensor',
        'traffic', 'transaction', 'staff',
        'schedule', 'basket', 'context',
        'ai', 'config'
    )),
    stream_id       UUID NOT NULL,
    version         BIGINT NOT NULL,
    event_type      TEXT NOT NULL,
    actor_type      TEXT NOT NULL CHECK (actor_type IN (
        'user', 'system', 'api_key', 'ai',
        'sensor', 'pos_system', 'weather_service',
        'forecast_engine', 'mining_engine',
        'scheduler', 'projection_engine'
    )),
    actor_id        TEXT,
    tenant_id       UUID,

    ce_source       TEXT NOT NULL,
    ce_type         TEXT NOT NULL,
    ce_time         TIMESTAMPTZ NOT NULL,
    ce_specversion  TEXT NOT NULL DEFAULT '1.0',

    data            JSONB NOT NULL,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (stream_type, stream_id, version)
) PARTITION BY RANGE (ce_time);

CREATE INDEX idx_events_stream ON event_store(stream_type, stream_id, version);
CREATE INDEX idx_events_tenant ON event_store(tenant_id, ce_time);
CREATE INDEX idx_events_type ON event_store(event_type, ce_time);

CREATE TABLE stream_snapshots (
    stream_type     TEXT NOT NULL,
    stream_id       UUID NOT NULL,
    version         BIGINT NOT NULL,
    state           JSONB NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (stream_type, stream_id, version)
);

CREATE TABLE projection_checkpoints (
    projection_name TEXT NOT NULL,
    partition_key   TEXT NOT NULL DEFAULT '_global',
    last_event_id   UUID NOT NULL,
    last_event_time TIMESTAMPTZ NOT NULL,
    state           JSONB NOT NULL DEFAULT '{}',
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (projection_name, partition_key)
);
```

## Event Taxonomy

### Store & Sensor Events
- `store_created` — {name, code, address, city, country, timezone, operating_hours}
- `store_updated` — {fields_changed}
- `sensor_installed` — {sensor_type, vendor, zone, location_in_store}
- `sensor_status_changed` — {old_status, new_status}

### Traffic Events
- `traffic_counted` — {store_id, sensor_id, zone, count_date, count_hour, entries, exits, staff_excluded, net_visitors, peak_occupancy, dwell_time_avg_seconds}
- `traffic_corrected` — {original_event_id, corrected_fields, reason}
- `traffic_estimated` — {store_id, count_date, count_hour, estimated_visitors, estimation_method, confidence}

### Transaction Events
- `transaction_recorded` — {store_id, external_id, transaction_type, total_cents, currency, items: [{sku, name, category, qty, price_cents}], items_count, staff_name, payment_method}
- `transaction_voided` — {original_transaction_id, reason}
- `transaction_returned` — {original_transaction_id, returned_items, refund_cents}

### Staff Events
- `staff_shift_started` — {store_id, staff_name, shift_start}
- `staff_shift_ended` — {store_id, staff_name, shift_end, hours_worked}
- `staff_count_updated` — {store_id, date, hour, actual_staff}

### Schedule Events
- `schedule_forecast_generated` — {store_id, forecast_date, hourly_predictions: [{hour, predicted_visitors, lower, upper}], forecast_model, model_version}
- `schedule_recommendation_generated` — {store_id, schedule_date, hourly_recommendations: [{hour, predicted_visitors, recommended_staff, staff_to_visitor_ratio}]}
- `schedule_accepted` — {store_id, schedule_date}
- `schedule_adjusted` — {store_id, schedule_date, adjustments: [{hour, old_staff, new_staff, reason}]}

### Basket Analysis Events
- `basket_analysis_completed` — {store_id, analysis_period_start, analysis_period_end, transaction_count, rules: [{antecedent, consequent, support, confidence, lift}], basket_metrics: {avg_items, avg_value_cents}, model_version}
- `layout_recommendation_generated` — {store_id, rule_id, recommendation, expected_impact}

### Context Events
- `weather_recorded` — {store_id, date, temp_c, condition, precipitation_mm, wind_kph}
- `promotion_started` — {store_id, name, discount_pct, channels, start_date, end_date}
- `promotion_ended` — {store_id, name}
- `event_noted` — {store_id, date, name, expected_impact}

### AI Events
- `ai_suggestion_generated` — {suggestion_type, store_id, title, description, evidence, confidence}
- `ai_suggestion_accepted` — {suggestion_id}
- `ai_suggestion_dismissed` — {suggestion_id, reason}
- `ai_anomaly_detected` — {store_id, anomaly_type, metric, expected_value, actual_value, possible_causes}
- `ai_conversion_insight_generated` — {store_id, period, insight_text, contributing_factors}

## Key Design Decisions

1. **Traffic counts as events** — traffic_counted events capture per-hour counts from sensors. Late or corrected sensor data fires traffic_corrected events; the projection replays to update metrics. No mutable traffic table.

2. **Conversion as a projection** — rm_conversion_timeseries materialises daily conversion rates by correlating traffic_counted and transaction_recorded events at matching store/date/hour boundaries.

3. **Schedule recommendations as events** — schedule_forecast_generated and schedule_recommendation_generated events create a permanent audit trail of every AI-generated roster. Store managers accept or adjust via schedule_accepted/schedule_adjusted events.

4. **Basket analysis as periodic events** — basket_analysis_completed events record association rule mining results with full rule metrics. rm_basket_insights provides the current view; historical analyses remain in the event store for trend comparison.

5. **Weather and promotions as context events** — weather_recorded and promotion_started events are correlated with traffic events in the rm_conversion_timeseries projection, enabling causal analysis of conversion changes.

6. **Anomaly detection as events** — ai_anomaly_detected events record unexpected traffic patterns, conversion drops, or staffing issues with possible causes derived from context events. The store manager sees these in rm_store_dashboard.open_alerts.

7. **Multi-store benchmarking as a projection** — rm_multi_store_benchmark aggregates per-store metrics daily, enabling regional manager comparisons without querying individual store projections.

8. **Privacy by design in events** — no PII in any event. Traffic events are anonymous aggregate counts. Transaction events carry staff_name for performance but no customer identity.

9. **Store dashboard as a real-time projection** — rm_store_dashboard maintains today's metrics, current-hour staffing state, and hourly breakdown, updated on every traffic_counted and transaction_recorded event for the real-time heads-up display.

10. **Schedule lifecycle as event sequence** — schedule_forecast_generated → schedule_recommendation_generated → schedule_accepted → schedule_adjusted → staff_count_updated creates a complete trail from forecast through recommendation to actual execution.
